## Format sugestii `l2_suggestion`
Wspólne kolumny: `kind`, `subject_type/subject_id`, `proposal jsonb`, `score` (skalibrowane prawdopodobieństwo 0..1, w bazie, nie na karcie), `rank` (1 = najlepsza), `status`, `evidence jsonb` = `{"facts": ["kwota co do grosza", "FV 12/2026 w tytule", "14× ten kontrahent → ta kategoria"], "badge": "high|medium|low", "precedents": 14, "hard": true|false, "margin": 0.31, "tags": ["ksef_number","mpp_block","invoice_number","amount_exact","single_open_invoice","rule:R-17@3"]}`. Odznaka: high = score ≥ 0,95 i hard; medium = score ≥ 0,7; low = reszta. Maks. 3 otwarte sugestie na podmiot i rodzaj (rank 1-3); „remis” = dwie sugestie o tym samym score w granicach 0,02 → żadna nie jest auto.

- `kind=match`, subject = transaction: `proposal = {"items": [{"document_id": uuid | null, "internal_record_id": uuid | null, "related_transaction_id": uuid | null, "amount_minor": int (znak: ujemny dla korekty w grupie), "difference_kind": "fee|fx|underpayment|overpayment|tolerance|correction|null", "difference_minor": int}], "final_status": "matched|no_document|own_transfer|to_clarify", "subtype": "zus|tax|fee|advance|deposit|card_awaiting|salary|refund|duplicate|interest|null", "awaiting_until": "YYYY-MM-DD|null"}`. Brak kandydata → pierwsza propozycja to `no_document` z podtypem (nie przypadkowa faktura).
- `kind=allocation`, subject = document_line | transaction | internal_record | document: `proposal = {"shares": [{"cost_object_id": uuid, "share": 0.6, "amount_minor": int}], "signal_strength": "A|B|C|D", "cascade_step": "line_description|offer_match|offer_value|person_days|equal|null"}`; UNASSIGNED to zwykły cost_object_id.
- `kind=cost_object_candidate`, subject = cost_object (wiersz `l3_cost_object` status candidate): `proposal = {"name", "attrs": {...}, "anchor": {"record_type", "record_id"}, "members": [{"record_type": "document_line|document|transaction|internal_record|email_case", "record_id", "link_strength": 0..1}], "weakest_link": 0.41, "revenue_minor": int, "cost_minor": int}`.
- `kind=category`, subject = transaction | document: `proposal = {"category": "ZUS", "subtype": null}`.
- `kind=rule_candidate`, subject = rule (wiersz `l3_rule` stage candidate): `proposal = {"rule_key", "question": "Czy nadawca X to zawsze ZUS?", "hits": 14, "total": 14, "counterparties": 1, "examples": [...3], "exceptions": [...]}`.

## Reguły `l3_rule`
`pattern jsonb = {"all": [{"field": "counterparty_id|op_type|title_regex|amount_minor|direction|intent|counterparty_kind", "op": "eq|regex|between|in", "value": ...}]}`; `action jsonb = {"kind": "category|match_strategy|allocation|final_status", ...}` np. `{"kind":"category","category":"ZUS"}`, `{"kind":"final_status","final_status":"no_document","subtype":"zus"}`, `{"kind":"match_strategy","strategy":"monthly_bulk"}`, `{"kind":"allocation","cost_object_id":...,"share":1}`. Etapy: candidate → hint → shadow → auto → suspended / dormant. Reguła wbudowana (z briefingu, zgoda użytkownika = briefing z 3.11) ma `rule_key` z prefiksem `builtin:` i jest zasiana w migracji z `method='human'`, `created_by='briefing-2026-11-03'`, stage `auto`; użytkownik może ją zawiesić.
Funkcja (4C implementuje w `kasa/core/rules/apply.py`; 4A/4B wołają przez `importlib` i pomijają warstwę, gdy modułu nie ma): `applicable_rules(conn, company_id, subject_type, subject_facts: dict) -> list[RuleHit(rule_id, rule_key, version, stage, action, evidence_count)]`.

## Zapis decyzji (L3)
- 4A: `kasa/core/matching/decide.py`: `apply_match(conn, suggestion_id, *, decided_by, method='human'|'rule', rule_id=None, rule_version=None, reason=None) -> decision_id` — tworzy wiersze `l3_match` (jedna `group_id` na sugestię), `l3_transaction_status`, oznacza sugestię accepted, pozostałe otwarte dla podmiotu rejected (`resolved_by_decision`), wpis w `l3_decision_log` (kind='match'). Automat: `method='rule'` z regułą `builtin:*` w stage auto, tylko gdy spełnione trzy warunki (score ≥ 0,995, hard, margin ≥ 0,2).
- 4B: `kasa/core/allocation/decide.py`: `apply_allocation(...)` analogicznie oraz `kasa/core/cost_objects_discovery/decide.py`: `approve_candidate / split / merge / reject / mark_distinct(conn, cost_object_id, ..., decided_by)` - zawsze human.
- 4C: `kasa/core/decisions.py`: `accept_suggestion(conn, suggestion_id, ...)` dyspozytor po `kind` do powyższych; `revoke_decision(conn, decision_id, decided_by, reason)` = nowa decyzja `revoke` + status revoked; `reject_suggestion`, `defer_suggestion`.
